## 2. Base de données et migrations

### Version du schéma

La version courante est **`schemaVersion = 4`** dans `app_database.dart`. La stratégie de migration (`MigrationStrategy`) contient des blocs conditionnels pour les versions 1→2, 2→3, et 3→4 :

- **v1→v2** : ajout de `lastPremiumDailyCoinsDate` sur `PlayerProfile`
- **v2→v3** : ajout de `rewardClaimed` sur `PermanentQuests` + backfill SQL
- **v3→v4** : ajout de `rewardClaimedIds` sur `DailyQuests` + backfill SQL
- Un commentaire indique qu'une table `MetaRunHistory` a été supprimée

### Analyse pour une première release

Puisqu'il s'agit d'une **première release sans utilisateurs à migrer**, tout utilisateur nouveau démarre à la version 4 via `onCreate` (qui crée toutes les tables à jour et seed les données). **Tout le code de migration `onUpgrade` est donc du code mort** pour cette release — il ne sera jamais exécuté.

**Recommandation** : Pour une première release, vous pouvez simplifier en supprimant les blocs `onUpgrade` et en gardant uniquement `onCreate`. Si vous prévoyez des mises à jour futures, conservez-les mais ajoutez un commentaire indiquant qu'ils sont inactifs pour la v1. Le commentaire sur `MetaRunHistory` peut être nettoyé.

**Recommandation** : Conserver les commentaires qui expliquent le "pourquoi" des décisions architecturales, mais nettoyer ceux qui racontent l'historique de débogage et les références aux Story IDs de développement.

## 6. Duplications de code

### 6.1 App bar pattern dupliqué

Chaque écran secondaire (`ShopScreen`, `BuildScreen`, `SettingsScreen`, `StatsScreen`, `QuestsScreen`) réimplémente son propre `_XxxAppBar` avec un bouton glass close + titre. Bien que le style soit cohérent, c'est de la duplication :

```dart
class _ShopGlassIconButton extends StatelessWidget { ... }
class _BuildGlassIconButton extends StatelessWidget { ... }
class _SettingsGlassIconButton extends StatelessWidget { ... }
class _StatsGlassIconButton extends StatelessWidget { ... }
```

**Recommandation** : Créer un widget réutilisable `ScreenAppBar(title, onClose)` partagé.

### 6.2 Mapping couleur biome dupliqué

La correspondance `BiomeType` → `Color` est définie dans `tile_component.dart` (`BiomeColor` extension) mais aussi re-définie manuellement dans `stats_screen.dart` (`_biomeColor()`). La version de `stats_screen.dart` devrait utiliser `BiomeColor` directement.

### 6.3 Pattern `_sentinel` pour copyWith

Le pattern `_sentinel` pour distinguer "paramètre non fourni" de "paramètre null" est réimplémenté dans `HexCell`, `PlacementState`, et `SessionState`. C'est un pattern idiomatique Dart mais répétitif.

### 6.4 Constantes dupliquées

Dans `bonus_animations.dart`, plusieurs constantes sont dupliquées depuis d'autres fichiers avec des commentaires explicites :
- `kCoinFlyDurationSec` = "dupliquée depuis CoinComponent"
- `kCoinSfxGapSec` = "dupliqué depuis AudioService.playCoinsGained"
- `kCoinSfxClipDurationSec` = constante mesurée
- `kMaxCoinSfxRepeats` = "dupliqué depuis AudioService"

**Recommandation** : Exposer ces constantes publiquement depuis leurs fichiers sources plutôt que de les dupliquer.

## 7. UI / UX

### 7.1 Design system

- **Esthétique cohérente** : glassmorphism (flou + transparence) avec un thème tropical (bleu nuit, teal, accents dorés). Tous les écrans secondaires partagent `TropicalBackground` + `GlassContainer`.
- **Design tokens centralisés** dans `core/colors.dart` (24 constantes de couleur nommées) — bonne pratique
- **Thème Material 3** défini dans `theme.dart` mais reste basique (placeholder). Le `themeMode` est forcé à `ThemeMode.dark` même si un thème light est défini.
- **Polices** : Pacifico (titres décoratifs) + Nunito (corps de texte), chargées depuis les assets locaux — bon choix pour la cohérence offline

### 7.2 Navigation

- Navigation par routes nommées (`/`, `/home`, `/game`) avec transitions personnalisées (`BlurFadePageRoute` et `HexWipePageRoute`) — excellent touch thématique
- Les écrans secondaires (Shop, Build, Settings, Stats, Quests) sont poussés en modal via `Navigator.push` depuis `HomeScreen`

### 7.3 Accessibilité et ergonomie

- **Plein écran immersif** (`SystemUiMode.immersiveSticky`) avec réapplication au retour au premier plan — approprié pour un jeu
- **Tailles de cibles tactiles** : le bouton pause a une zone de tap plus grande que le rendu visuel (48px vs 36px) — bonne pratique
- **Feedback haptique** systématique sur les boutons via `buttonTapFeedback()` — bon UX pour un jeu mobile
- **Tutoriel first-launch** avec highlight suivant les vraies positions des widgets (GlobalKey) plutôt que des pourcentages arbitraires — solide
- **Absence d'accessibilité** : pas de `Semantics`, pas de support `TalkBack`/`VoiceOver` visible, pas de tests d'accessibilité. Pour un jeu cozy ce n'est pas bloquant mais c'est une lacune.

### 7.4 Points d'attention UX

- **Mode immersif permanent** : peut frustrer certains utilisateurs qui veulent voir l'heure ou le niveau de batterie. Envisager un toggle dans les réglages.
- **Animations de transition** : le blur à 18 sigma en release peut être coûteux sur des appareils bas de gamme. La valeur est réduite à 8 en debug (`kDebugMode ? 8 : 18`) — c'est l'inverse de ce qu'on attendrait (debug devrait être plus léger).
- **Sound design** : Pitch variance aléatoire sur les bruitages pour éviter la lassitude — excellent détail
- **Onboarding** : le tutoriel suit une séquence linéaire avec possibilité de passer — bien adapté

## 9. Analyse supplémentaire

### 9.1 Sécurité

- **IDs AdMob de production en clair** dans `constants.dart` — c'est standard pour AdMob (les IDs ne sont pas secrets) [1]
- **Aucun secret codé en dur** — les clés Firebase sont injectées via CI secrets [1]
- **Firebase Crashlytics** capture les erreurs mais `AnalyticsService.initialize()` catche silencieusement les échecs — bon pour la résilience [1]

### 9.2 Performance

- **Optimisation Flame** : le flag dirty `_previewDirty` évite de relire les providers à chaque frame — bonne pratique [1]
- **Ondulation du bord bas** désactivée au-delà de 150 tuiles (`kEdgeWaveTileCountThreshold`) pour préserver les FPS — pragmatique [1]
- **RepaintBoundary + Opacity(0.999)** dans `GlassContainer` pour contourner un bug Flutter de BackdropFilter — workaround documenté et justifié [1]
- **Sprite coin partagé** (static `_sprite`) chargé une seule fois — bon pour la mémoire [1]

### 9.3 CI/CD

Le pipeline CI est bien configuré [1] :
- `flutter analyze --no-fatal-infos` + `flutter test --coverage` sur chaque PR
- Build debug sur `develop`, build release + AAB sur `master`/tags
- Injection de `google-services.json` via secrets
- Gestion du keystore de signing (avec fallback debug)
- Création automatique de GitHub Releases avec artifacts APK + AAB
- Versioning par timestamp CI pour le build number

### 9.4 Configuration du linter

`analysis_options.yaml` active `strict-casts`, `strict-inference`, `strict-raw-types` — excellent pour la qualité du code. Règles supplémentaires pertinentes : `prefer_const_constructors`, `require_trailing_commas`, `sort_child_properties_last` [1].

### 9.5 `google_fonts` non déclaré

Le fichier mort `upgrades_screen.dart` importe `package:google_fonts/google_fonts.dart` qui n'est pas dans `pubspec.yaml`. Si ce fichier est supprimé (recommandé), le problème disparaît. Sinon, `flutter analyze` échouerait si le fichier était jamais importé [1].

### 9.6 Gestion d'état

Le projet utilise un **mix de Riverpod annotation-based** (`@riverpod`, `@Riverpod(keepAlive: true)`) et de **Riverpod manuel** (`NotifierProvider`, `Provider`, `StreamProvider`). Ce n'est pas un problème en soi mais l'uniformité serait préférable. Les providers générés nécessitent `build_runner` — le `pubspec.lock` verrouille correctement les versions [1].

## 11. Conclusion

Le projet **Hex Cozy Games** est de **bonne qualité globale** pour une première release. L'architecture est bien organisée, la séparation des préoccupations est claire, les tests couvrent raisonnablement la logique métier (~243 tests pour ~24k lignes de code), et l'UI présente une esthétique cohérente et soignée [1]. Les principaux axes d'amélioration sont l'élimination du code mort (notamment `upgrades_screen.dart`), la réduction de la taille des fichiers UI les plus gros, le nettoyage des commentaires historiques, et l'ajout de tests pour la logique de récompense de placement (`placement_commit.dart`) qui est le cœur du gameplay mais manque de couverture directe [1].
